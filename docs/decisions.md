## Продукт

**Суть:** инструмент автоматической проверки публичных сайтов на соответствие 152-ФЗ (персональные данные, РФ).

**Аналогии:**
- 1С — пользователь не думает об изменениях законов, обновления приходят изнутри
- Гарант — подписочная модель, актуальность базы

**Пользователь вводит URL — получает отчёт:** что нарушено, где, какой штраф, как исправить.

---

## Пользователи

- Разработчик сайта
- Юрист
- Владелец сайта

Все три — не технические специалисты в части 152-ФЗ. Отчёт должен быть понятен без знания закона.

## Бизнес-модель

Коммерческий продукт. Три модели монетизации:
1. Подписка на инструмент (десктоп / онлайн)
2. Подписка на обновления базы критериев
3. Разовая оплата за отчёт (без покупки продукта — клиент платит за результат)

## Law Monitor — детальная архитектура

**Источник:** publication.pravo.gov.ru
- Публичное API (без ключа, JSON): `publication.pravo.gov.ru/api/`
- RSS-лента: `publication.pravo.gov.ru/rss`

**Три шага процесса:**

**Шаг 1 — Мониторинг (автоматический, раз в месяц)**
- Опрашиваем API/RSS publication.pravo.gov.ru
- Фильтруем по ключевым словам: "152-ФЗ", "персональных данных", "13.11 КоАП"
- Если изменений нет — завершаем тихо, пишем в лог
- Если изменение найдено — переходим к шагу 2

**Шаг 2 — Анализ (полуавтоматический)**
- Скачиваем текст нового закона/поправки
- Передаём AI для анализа: что именно изменилось, какие блоки YAML затронуты
- AI формирует конкретные предложения правок в law_base/blocks/*.yaml

**Шаг 3 — Подтверждение (человек)**
- Оператор получает уведомление с описанием изменений и предложенными правками
- Подтверждает или отклоняет правки
- Только после подтверждения изменения попадают в базу и к пользователям

**Почему шаг 3 обязателен:**
Продукт сообщает о штрафах клиентам. Ошибка в базе = ошибка в отчёте. Автоматическое обновление без проверки человеком недопустимо.

**Компоненты модуля:**
- `law_monitor/fetcher.py` — опрос API и RSS
- `law_monitor/parser.py` — извлечение текста закона
- `law_monitor/analyzer.py` — передача текста AI, получение предложений правок
- `law_monitor/notifier.py` — уведомление оператора
- `law_monitor/scheduler.py` — расписание (раз в месяц, GitHub Actions)

## Law Base MVP — верифицированные критерии

Источник: КонсультантПлюс, КоАП РФ ст. 13.11, актуальная редакция с учётом ФЗ-420 от 30.11.2024 (вступил в силу 30.05.2025).
Штрафы указаны для юридических лиц.

| ID | Нарушение | Норма 152-ФЗ | Статья КоАП | Штраф (юрлицо) |
|----|-----------|-------------|-------------|----------------|
| A1 | Нет политики ПДн / нет публичного доступа к ней | ст. 18.1 ч.2 | ч.3 ст.13.11 | 30 000 – 60 000 руб. |
| B1 | Чекбокс согласия предустановлен (checked) | ст. 9 | ч.2 ст.13.11 | 300 000 – 700 000 руб. |
| B2 | Форма с ПДн без чекбокса согласия | ст. 9 | ч.2 ст.13.11 | 300 000 – 700 000 руб. |
| B3 | Нет ссылки на политику рядом с формой (нарушение состава согласия) | ст. 9 ч.2 | ч.2 ст.13.11 | 300 000 – 700 000 руб. |
| C1 | Аналитика / cookie без согласия пользователя | ст. 9 | ч.1 ст.13.11 | 150 000 – 300 000 руб. |

**Принцип верификации:** каждый критерий привязан к конкретной части статьи КоАП. Сумма штрафа берётся из первоисточника, не из вторичных статей. При любом сомнении — проверять КонсультантПлюс напрямую.

## Технические решения — Detector Engine (сессия 2, 2026-05-22)

### validated.model_dump() вместо сырого YAML-dict
`DetectorEngine._violations` хранит `validated.model_dump()`, а не исходный dict из YAML.
**Причина:** Pydantic заполняет поля с дефолтами (например, `is_recommendation: False`) только в модели. Сырой dict не содержит поле если оно отсутствует в YAML. Это вынуждало дублировать дефолт в `_build_result()`. С `model_dump()` дефолты гарантированно присутствуют — дублирование устранено.

### get("violations") or [] вместо get("violations", [])
`dict.get(key, default)` возвращает `default` только если ключ ОТСУТСТВУЕТ. Если ключ есть со значением `None` (YAML: `violations:` без значения), возвращается `None`. Итерация по `None` → `TypeError`.
**Правило:** для защиты от `null`-значений использовать `d.get(key) or []`.

### B1/B2 взаимоисключение через _apply_b_mutex()
B2 (нет чекбокса) и B1 (чекбокс предустановлен) физически невозможны одновременно для одной формы. Без защиты оба детектора могут сработать на одной форме при ошибке в логике одного из них.
**Решение:** `run_all()` вызывает `_apply_b_mutex()` после прогона всех детекторов. Матчинг форм — по `evidence["form_index"]` (0-based индекс в `soup.find_all("form")`). При конфликте приоритет у B2.
**Обязательное требование к B-детекторам:** включать `form_index: int` в `evidence`. Без него mutex не сработает.

### HTTP в детекторах — только httpx
`requests` в проекте нет. `httpx` присутствует в `requirements.txt` (нужен FastAPI). Для HTTP-запросов внутри детекторов используется `httpx.Client` (синхронный режим).

### A1 — base_url из network_log[0]
Детектор A1 для шагов 3 (known_urls) и 4 (verify_accessible) требует абсолютные URL.
**Конвенция:** `network_log[0]["url"]` — запрос к сканируемой странице. `_extract_base_url()` извлекает `scheme://host`.
**Компромисс:** если `network_log=[]` (в тестах), шаги 3 и 4 пропускаются. Тесты проверяют только HTML-логику (шаги 1–2) с `verify_accessible=False`.

### A1 — verify_accessible=True как защита от ложных срабатываний
Ключевое слово "политика" совпадает с "политика возврата", "политика доставки" и др. Без верификации содержимого детектор даст ложный отрицательный результат (скажет "всё ок", хотя политики ПДн нет).
`verify_accessible=True` включает шаг 4: GET-запрос + проверка наличия `content_min_match` ключевых слов ("персональных данных", "обработка", "оператор", "согласие"). Страница с политикой возврата эти слова не содержит.
**В production:** `verify_accessible` всегда `true` (значение в A.yaml). В тестах отключается явно.

## Технические решения — детекторы B1/B2/B3 (сессия 3, 2026-05-22)

### alternative_consent → is_recommendation=True, не severity override
B2 при обнаружении альтернативного согласия (текст у кнопки submit) первоначально переопределял `result["severity"] = "warning"`. Это мутировало Pydantic-валидированный dict после сборки — Report Engine получал B2 иногда как "critical", иногда как "warning".
**Решение:** `result["is_recommendation"] = True`. Severity остаётся из YAML ("critical"), флаг меняет трактовку. Поле `is_recommendation` именно для этого существует в модели.

### Русская морфология в YAML-ключевых словах — использовать стемы
Одиночное слово в именительном падеже не совпадает с другими падежами как подстрока:
- "политика" НЕ совпадает с "политикой", "политике", "политику"
- "согласен" НЕ совпадает с "согласна", "согласны"
**Правило:** для русскоязычных ключевых слов использовать усечённую форму (стем):
- "политика" → "политик" (покрывает все падежи)
- "конфиденциальность" → "конфиденциальност"
- "согласен"/"согласие" → "соглас"
Это применено в A.yaml (keywords), B.yaml (consent_keywords, policy_keywords).

### Тест на каждую нетривиальную ветку кода
B2 alternative_consent путь (`is_recommendation=True`) не имел теста после исправления.
**Правило:** любая ветка с изменённым поведением (особенно флаги нарушение/рекомендация) требует отдельного теста. Код без теста считается непроверенным.

## Технические решения — сессия 4 (2026-05-22)

### evidence["found"] — удалено
Поле `found` в `evidence` имело обратную семантику: B1 использовал `found=True` ("нашли плохое"), A1/B2/B3 — `found=False` ("не нашли хорошее"). Поле не несёт смысла: сам факт присутствия результата в списке нарушений означает "нарушение найдено". Report Engine не нуждается в `found` для отображения — достаточно `detail` и специфических полей (`checkbox_text`, `form_index`, `alternative_consent_text`).
**Правило:** `evidence` содержит описательные поля. Факт нарушения — в структуре списка, не в полях.

### C2 — отключён (enabled: false)
C2 (зарубежная аналитика → локализация) имеет высокий риск ложноположительных результатов. Штраф 1–6 млн руб. при неточной детекции неприемлем для коммерческого продукта.
**Правило:** детектор с потенциалом ложноположительного срабатывания на крупный штраф → `enabled: false` до верификации правоприменительной практики.

- `logger` добавлен но не используется → мёртвый код. Проверять что каждый импорт используется.
- `from bs4 import BeautifulSoup` на верхнем уровне → нарушает `TYPE_CHECKING`. Проверять в каждом новом файле.

- Комментарий с описанием поведения кода → перепутал случаи. Верифицировать логику явно перед написанием.
- `grep` с скобками в паттерне → ложные негативы. Использовать `grep -F` для фиксированных строк.
- `dict.get(key, [])` не защищает от `null`: если ключ есть со значением `None` — возвращается `None`. Паттерн: `d.get(key) or []`.
- Хранить сырой YAML-dict вместо `validated.model_dump()` → дефолты Pydantic не попадают в dict. Всегда хранить `model_dump()`.
- HTTP в детекторах — только через `httpx`. `requests` в проекте нет.
- `result["severity"] = "warning"` после `_build_result` → мутирует валидированный dict. Использовать `result["is_recommendation"] = True`.
- Русские ключевые слова в именительном падеже не совпадают с другими падежами. Использовать стемы ("политик", "соглас", "конфиденциальност").
- `evidence["found"]` с разной семантикой в разных детекторах → путаница в Report Engine. Решение: убрать поле entirely, использовать описательные поля.
- Детектор с риском ложноположительного результата на крупный штраф → `enabled: false` по умолчанию, не код-заглушка.
- Импорты детекторов после Pydantic-моделей в engine.py → ruff E402. Все imports — строго в начале файла.
- `pytest-asyncio` в requirements.txt, но не установлен → `asyncio_mode` warning на каждый запуск тестов. Проверять установку всех зависимостей из requirements.txt.

## Технические решения — сессии 7–8 (2026-05-22)

### PlaywrightWrapper — async context manager, не функция
PlaywrightWrapper управляет браузером. Браузер создаётся один раз при `__aenter__` и живёт до `__aexit__`. Создавать браузер на каждый запрос (`async with PlaywrightWrapper()` внутри scan()) → ~1-2 секунды накладных расходов на запрос.
**Правило:** Scanner и PlaywrightWrapper — context manager'ы. Жизненный цикл браузера совпадает с жизненным циклом приложения (FastAPI lifespan).

### Scanner как async context manager для FastAPI lifespan
```python
@asynccontextmanager
async def lifespan(app):
    async with Scanner() as scanner:
        app.state.scanner = scanner
        yield
```
DetectorEngine и браузер создаются один раз при старте. `app.state.scanner` доступен во всех хэндлерах.

### asyncio.to_thread для run_all
Детектор A1 делает синхронные HTTP-запросы (`httpx.Client`). `DetectorEngine.run_all()` синхронный. Вызов напрямую из `async def scan()` заблокирует event loop на каждый реальный скан.
**Правило:** `await asyncio.to_thread(self._engine.run_all, soup, network_log)`.

### robots.txt через asyncio.to_thread с таймаутом
`RobotFileParser.read()` из stdlib — синхронный, может зависнуть. Оборачивается в `asyncio.wait_for(asyncio.to_thread(rp.read), timeout=5.0)`. Любая ошибка или таймаут → разрешить сканирование (стандартная практика).

### CORS — allow_origins=["*"] для MVP
Без CORS middleware браузерный React UI не может вызвать API. `allow_origins=["*"]` на MVP допустим. При деплое сужать до домена UI.

### ReportEngine.build() — разделение violations/recommendations
Поле `is_recommendation` (bool) — единственный разделитель. Нарушения и рекомендации разделяются в `build()`, не в детекторах. `status`: `"compliant"` | `"recommendations_only"` | `"violations_found"`.
