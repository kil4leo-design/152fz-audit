# decisions.md — Память проекта

> Этот файл читается в начале каждой рабочей сессии с AI.
> Каждое принятое решение фиксируется здесь с обоснованием.
> Без этого файла AI не имеет контекста проекта.

---

## Продукт

**Суть:** инструмент автоматической проверки публичных сайтов на соответствие 152-ФЗ (персональные данные, РФ).

**Аналогии:**
- 1С — пользователь не думает об изменениях законов, обновления приходят изнутри
- Гарант — подписочная модель, актуальность базы

**Пользователь вводит URL — получает отчёт:** что нарушено, где, какой штраф, как исправить.

---

## Пользователи

- Разработчик сайта
- Юрист
- Владелец сайта

Все три — не технические специалисты в части 152-ФЗ. Отчёт должен быть понятен без знания закона.

---

## Бизнес-модель

Коммерческий продукт. Три модели монетизации:
1. Подписка на инструмент (десктоп / онлайн)
2. Подписка на обновления базы критериев
3. Разовая оплата за отчёт (без покупки продукта — клиент платит за результат)

---

## Функциональность

- Проверка одного сайта по URL
- Проверка списка сайтов по шаблону
- Разовый отчёт
- История проверок (динамика соответствия)
- Выбор блоков проверки (А-Ж) или полная проверка

---

## База критериев 152-ФЗ

Живёт в открытых источниках:
- https://rpn.gov.ru/upload/iblock/3cc/jy73a14zc99w4bm8xnc22y2m7iwpusar/248_FZ.pdf
- https://minfin.gov.ru/ru/document?id_4=301238
- https://digital.gov.ru/documents/o-personalnyh-dannyh/

Структура критериев — блоки А-Ж (выявлены в предыдущем диалоге).

**Программа сама следит за изменениями законов** и обновляет базу критериев (модуль Law Monitor — не в MVP).

## Стек

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Сканирование | Python + Playwright | Видит динамический JS-контент (cookie-баннеры, формы). requests+BeautifulSoup не видит JS-рендеринг |
| API | FastAPI | async важен при параллельном сканировании. Автодокументация нужна для модели "оплата за отчёт" |
| БД | SQLite → PostgreSQL | SQLite для старта (нет сервера, просто). Миграция на PostgreSQL при появлении подписочной модели |
| UI | React | Однородный JS на фронте |
| Десктоп (перспектива) | Electron или Tauri | Оборачивает веб-версию, не нужно писать заново |

## Архитектура — модули

| Модуль | Назначение | В MVP |
|--------|-----------|-------|
| Scanner | Принимает URL, загружает страницу, прогоняет детекторы | ✅ |
| Detector Engine | Набор детекторов по блокам А-Ж, включается/выключается независимо | ✅ |
| Law Base | База критериев: нормы, штрафы, ссылки на статьи | ✅ |
| Report Engine | Формирует читаемый отчёт из результатов сканера | ✅ |
| UI | Веб-интерфейс: поле URL + кнопка + результат | ✅ |
| Law Monitor | Мониторинг изменений в источниках законов | ❌ |
| History | История проверок, динамика | ❌ |
| Auth + Billing | Подписка, доступ, оплата | ❌ |

**Принцип:** Scanner не знает ничего про UI и API. Модули независимы.

## Дорожная карта

**Этап 0 — Инфраструктура**
GitHub repo, структура папок, ветки, защита main, CI (линтер + тесты), шаблоны Issues и PR.

**Этап 1 — Detector Engine + Law Base (параллельно)**
Один детектор = одна запись в Law Base = два теста (нарушение + соответствие).
Фабричный паттерн. Только статически детектируемые критерии из блоков А-Ж.

**Этап 2 — Scanner + Report Engine + минимальный UI (параллельно)**
Рабочий продукт который можно показать пользователю.
Форматы отчёта: веб + JSON.

**Этап 3 — Доработка UI**
На основе обратной связи от первых пользователей. Подготовка к онлайн-деплою.

## Правила работы с AI

1. Каждую сессию передавать AI файлы `docs/decisions.md` и `docs/roadmap.md`
2. Каждое принятое решение фиксировать в этом файле сразу
3. Каждый модуль разрабатывается отдельно в отдельной сессии
4. AI не поддакивает — критически оценивает предложения
5. Фантазия = ошибка. Только факты из контекста
