## EC-1 — C1 на chipdip.ru: реальное нарушение или ложное срабатывание?

**Дата:** 2026-05-23

**Что произошло:**
Сканер нашёл C1 на chipdip.ru — «Сбор аналитики и cookie без согласия пользователя».

В реальном HTML (получен из браузера F12) видны три аналитических счётчика,
инициализируемых в `<head>` и `<body>` **до** взаимодействия пользователя с cookie-баннером:

- `mc.yandex.ru/metrika/tag.js` — Яндекс.Метрика: `ym(1617813, "init", ...)`
- `top-fwz1.mail.ru/js/code.js` — Mail.ru Top: `_tmr.push(...)`
- `window.dataLayer = []; gtag('js', new Date())` — Google Analytics структура

На странице есть cookie-баннер с кнопкой «OK» и ссылкой на политику.
Также в JS: `chipdip.cookieConsent=1` — возможно, флаг сохранённого согласия.

**Вопрос:**
Действительно ли chipdip.ru грузит аналитику до согласия (нарушение 152-ФЗ ст. 9)?
Или там реализована отложенная загрузка (lazy init), которую сканер не видит?

**Что нужно выяснить:**
1. Как работает `chipdip.cookieConsent=1` — это признак уже данного согласия или флаг по умолчанию?
2. Загружаются ли скрипты аналитики при первом визите (без cookies) или только после согласия?
3. Есть ли у Яндекс.Метрики режим «не собирать данные до согласия» — и включён ли он здесь?
4. Правоприменительная практика: признаёт ли Роскомнадзор загрузку скрипта аналитики
   нарушением, если сбор данных настроен начинаться только после согласия?

**Источники для поиска:**
- Документация Яндекс.Метрики: режим «без cookies» / отложенная активация
- Разъяснения Роскомнадзора по cookie и аналитике
- Судебная практика по ч.1 ст.13.11 КоАП в части cookie

**Влияние на детектор C1:**
Если отложенная загрузка является достаточной мерой → C1 должен проверять
не просто факт загрузки скрипта, а факт передачи данных до согласия (сложнее).
Если нет → текущая логика C1 корректна.

---

**Решение (2026-05-23):** Закрыт. Детектор C1 доработан — реализован Вариант B.

**Ключевой факт:** Яндекс.Метрика defer mode загружает `tag.js` немедленно, откладывая
только `ym("init", ...)`. Загрузка файла и сбор данных дают разные URL в network_log:
- `mc.yandex.ru/metrika/tag.js` — загрузка скрипта (серая зона)
- `mc.yandex.ru/watch/COUNTER_ID` — реальный сбор данных (нарушение)

Старый детектор не различал эти случаи → ложные срабатывания на defer mode.

**Что изменено:**
- `law_base/blocks/C.yaml`: добавлен `data_collection_patterns` — список URL-паттернов
  реального сбора данных (`/watch/`, `/g/collect`, `top-fwz1.mail.ru/counter` и др.)
- `scanner/detectors/html_cookie_banner_missing.py`: новая логика —
  - domain hit + совпадение с `data_collection_patterns` → **нарушение**
  - domain hit без совпадения (только загрузка скрипта) → **рекомендация**
- Добавлены 2 теста, обновлены 2 (21 тест, все проходят)

**chipdip.ru**: не удалось проверить конкретные URL из network_log (нет сохранённых данных
скана). При следующей проверке chipdip.ru результат будет корректным.

## EC-2 — B2 на citilink.ru: недостаточно данных в evidence для ручной проверки

**Дата:** 2026-05-24

**Что произошло:**
Сканер нашёл B2 на citilink.ru (`form_index: 1`). B3 при этом прошёл — значит рядом
с формой есть ссылка на политику, но нет чекбокса согласия.

В evidence детектор указывает только `form_index` и `detail`. Какие именно поля ПДн
были найдены в форме — неизвестно. Пользователь не смог идентифицировать форму визуально.

**Вопрос:**
Какая именно форма на главной citilink.ru имеет `form_index: 1`? Является ли B2 реальным
нарушением или ложным срабатыванием (например, форма поиска с полем `name`)?

**Что нужно выяснить:**
1. Добавить в evidence B2 список найденных PD-полей (`matched_fields`) — для ручной проверки
2. Проверить в DevTools на citilink.ru: найти все `<form>` элементы, посмотреть на второй (index 1)
3. Является ли форма входа в аккаунт в шапке нарушением B2 — требует ли она чекбокс согласия

**Влияние на детектор B2:**
Добавить `matched_fields: list[str]` в evidence — список имён полей ПДн, которые
сработали как триггер. Это улучшит объяснение результата пользователю и упростит
ручную верификацию.

---

**Решение (2026-05-24):** Закрыт. `matched_fields` добавлен в evidence B2.

Формат: `["type=email", "name=phone", "placeholder=Ваш телефон"]`.
`_form_has_pd_fields` заменена на `_get_matched_pd_fields` — возвращает список вместо bool.
Список включается в evidence как для нарушения, так и для рекомендации (alternative_consent).
Добавлены проверки matched_fields в тестах (26 тестов, все проходят).
